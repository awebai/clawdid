# UX review (Playwright) — 2026-02-22

Scope:
- SPA dev UI (`frontend/`) on `http://localhost:18113`
- Marketing site (`site/`) on `http://localhost:18114`

Captured screenshots live in `artifacts/ux-2026-02-22/`.

## How to reproduce locally

1. Start services:
   - `make dev-db-up`
   - `make dev-backend`
   - `make dev-frontend`
   - `make dev-site`
2. Optional: seed a demo identity for “success” flows:
   - `POST /v1/did` with a valid `proof` (Ed25519 signature over the canonical log entry payload).

Example identity used during this review:
- `did:claw:xQ5nm3hhNVSFKhMnhys42pJAJ5F`
- `did:key:z6Mkv1o2GEgtXjFdEMfLtupcKhGRydM8V7VHzii7Uh4aHoqH`

## High-level UX goals (what “good” looks like)

1. A newcomer understands **what ClaWDID is** and what it is **not** (launch transparency limits).
2. A developer can quickly:
   - derive stable IDs from `did:key`
   - look up a `did:claw` → current `did:key`
   - verify the audit log end-to-end
3. Verifier UX clearly separates:
   - **cryptographic verification** that can be done offline
   - **trust/transparency guarantees** that require witnesses (future)

## Findings (prioritized)

### P1 — SPA: mobile navigation compresses; no responsive menu

On a 390×844 viewport the top nav items are cramped and can wrap awkwardly.

Impact:
- first-time users on mobile may not discover pages reliably

Suggestion:
- replace the top nav with a hamburger menu (or collapsible menu) below `sm`
- add `aria-current="page"` (or equivalent) so the active tab is obvious

Screenshots:
- `artifacts/ux-2026-02-22/spa-lookup-mobile.png`
- `artifacts/ux-2026-02-22/spa-verify-log-mobile.png`
- `artifacts/ux-2026-02-22/spa-derive-mobile.png`

### P1 — SPA: error states are raw HTTP strings / JSON

The lookup error state shows raw `400 Bad Request: {"detail":...}`.

Impact:
- users do not know what to do next
- implies fragility / “developer-only” experience

Suggestion:
- parse `{detail: ...}` and show a human message with a clear next action
- add client-side validation for the `did:claw:` / `did:aw:` prefix before firing the request

Screenshots:
- `artifacts/ux-2026-02-22/spa-lookup-error-badid-desktop.png`

### P1 — SPA: input fields rely on placeholder as label (a11y)

The textbox is identified by placeholder text only.

Impact:
- screen readers and form history/autofill are worse

Suggestion:
- add explicit `<label>` text (“Stable ID (did:claw:…)”) and keep placeholder for example only

### P2 — SPA: “OK_VERIFIED” needs “what exactly was verified?” copy

The “OK_VERIFIED” badge is good, but we should be explicit:
- verified: signature, entry hash, and mapping consistency
- not verified (at launch): absence of equivocation (no witness quorum / checkpointing yet)

Suggestion:
- add a short “Verified means …” line + a link to a “Security model” page (or docs)

Screenshots:
- `artifacts/ux-2026-02-22/spa-lookup-result-desktop.png`
- `artifacts/ux-2026-02-22/spa-verify-log-result-desktop.png`

### P2 — SPA: copy-to-clipboard + truncation for long identifiers

For DIDs/keys/hashes, provide:
- “copy” affordance per field
- truncated display with hover-to-reveal (or click-to-expand)

Impact:
- makes the SPA usable as a real tool, not just a demo

### P1 — Marketing: missing favicon causes console 404

Console shows a missing `favicon.ico`.

Impact:
- minor, but noisy and low polish

Suggestion:
- add a tiny favicon and link tags

### P1 — Marketing: Docs page lists paths but they aren’t clickable docs

Current docs list shows `sot.md`, `ROADMAP.md`, etc. as inline code without links.

Impact:
- people can’t actually read the docs on the marketing site

Suggestion:
- either:
  - render these markdown docs into the Hugo site (preferred), or
  - link to GitHub for now (acceptable but less ideal)

Screenshots:
- `artifacts/ux-2026-02-22/site-docs-desktop.png`
- `artifacts/ux-2026-02-22/site-docs-mobile.png`

### P2 — Marketing: add a clear CTA to the SPA verifier

If the marketing site is the public entrypoint, it should link to the interactive verifier.

Suggestion:
- add “Try the verifier” (CTA) on home, pointing at the SPA (likely a subdomain in prod)
- add “Run locally” steps for OSS contributors

## Notes / opportunities

- Consider adding a tiny “Demo” section in the SPA with a known test DID and a button to prefill.
- Consider a single short “Security model” doc (1 page) linked from both site + SPA.
